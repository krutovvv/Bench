# Тред заново: разбор и план

## 1. Почему агент на Qwen делает 40–140 шагов на простую правку

Это не догадка, а подсчёт по `~/.bench/pi.sqlite`, тред 8057 (15 ваших сообщений за день).

| Сообщение | Вызовов инструментов | Из них — чтение исходников gpui в `~/.cargo/registry` |
|---|---|---|
| Утилиты не вставляются | 43 | 7 |
| Удаление FTP | 29 | 0 |
| Редактирование FTP | 67 | 1 |
| Клик по экшенам кидает в другой тред | 48 | 2 |
| **Интервалы в поле ввода** | **72** | **37** |
| Статус MCP | 140 | 0 (но 22 раза `cargo build`, 94 чтения кусков `project_env.rs` + `project_list.rs`) |
| Отступ под полем | 29 | 12 |

Причины, по убыванию веса:

1. **«225 шагов за 40 минут» — это не одна задача.** Ваши сообщения из очереди Pi подхватывает внутри
   того же прогона, а счётчик шагов и таймер в Bench считают *прогон*, а не *сообщение*. Задача про
   интервалы на самом деле заняла 72 вызова и 13 минут — тоже много, но в три раза меньше, чем видно.
   Это тот же корень, что и «шаги куда-то делись»: тред не знает, какой шаг к какому сообщению относится.
2. **Ответа нет в проекте — он в зависимостях.** Половина задачи про интервалы ушла на поиск
   межстрочного интервала `Input` внутри `gpui-component`/`gpui-base` в `~/.cargo/registry`. Ни одна
   строка проекта не говорит «текст треда — 15 px, интервал 1.5, поле ввода берёт его отсюда».
   Типографика размазана по `chat.rs`, `composer.rs`, `media.rs`, `mod.rs`.
3. **Большие файлы.** `app.rs` 2787 строк, `chat.rs` 1901, `project_env.rs` 1612, `project_list.rs`
   1470. Маленькая модель не может держать их целиком и читает по 30 строк `sed -n`, по 50 раз.
4. **Комментарии-эссе.** Каждый комментарий и коммит — абзац истории («до этого было так, потом…»).
   Для модели это шум: она читает историю правок вместо того, что код делает сейчас.
5. **Скилл на 14 000 строк** (`bench-kit/references`). Нужный факт в нём есть не всегда, а найти его
   дороже, чем грепнуть код.
6. **Сжатия контекста.** В треде 9 compaction — после каждой агент заново изучает те же файлы.
   Один тред на 15 разных задач для маленькой модели — плохо: новая задача = новый тред.

MCP с «картой проекта» не нужен: нужна структура, где карта очевидна из дерева файлов, и одна
страница `docs/map.md` с ответами на вопросы, которые агент реально задавал (где шрифт, где
порядок треда, где строка MCP).

## 2. Почему тред глючит: три источника правды

Сейчас тред — это три списка, которые сводятся при рисовании эвристиками:

- `turns: Vec<Turn>` — пары «сообщение человека → шаги → ответ», которые `history.rs` *заново
  угадывает* из плоского списка сообщений в старом формате Hermes (`role/tool_calls/row_id`,
  где `row_id` — просто счётчик, не id записи);
- `queue: Vec<(id, mode, text)>` — очередь отдельно, внизу;
- `inserts` с полем `after: usize` — «после скольких сообщений человека стоит», то есть позиция
  считается, а не хранится.

Плюс живые события тоже в формате Hermes (`message.start`, `tool.start`, `message.user`), плюс
агент дублирует всё во второе хранилище (`store.addMessage`), плюс `thread_cache`, `settle`,
`rows_shift`, `past_end` — заплатки, чтобы склейка не прыгала на экране. Каждая правка «прыжка»
лечит одно место склейки и ломает другое. Отсюда «очередь пропала», «сообщение улетело вверх»,
«кинуло в другой тред».

Тем временем у Pi уже есть ровно то, что нужно: **журнал**. Каждая запись (`pi.user`,
`pi.assistant`, `pi.tool-result`, `bench.insert`) имеет возрастающий id, а `subscribeCommits`
отдаёт каждую новую. Очередь — это `InboxDoc`, состояние вставок — документ `bench.inserts`.
Мы просто не передаём это в Bench как есть.

## 3. Как будет

### Модель (одна, как лог Kafka)

Тред — **один упорядоченный список элементов**. У каждого элемента постоянный ключ, и порядок
определяется только ключом, никогда — подсчётом:

```
key = (seq, sub)
  seq — id записи Pi (у журнала) или  ∞ + позиция в InboxDoc (у очереди)
```

Элементы:

| Элемент | Откуда | Как выглядит |
|---|---|---|
| Сообщение человека | `pi.user` | ваш текст |
| Сообщение в очереди | элемент `InboxDoc` | тот же вид, статус «в очереди», стоит после журнала |
| Работа агента | `pi.assistant` с вызовами + `pi.tool-result` между двумя ответами | свёрнутая строка «N шагов · 12 с», считается **на это сообщение** |
| План агента | шаги `todo` (не журнал), с датой, когда агент их написал (`todos_at`) | строка «ПЛАН · 3/7» **в том ходе, где она родилась**: перед следующим сообщением и перед очередью; пока ход живой — сразу за его работой. Нет запуска или не осталось шагов — строки нет |
| Ответ агента | `pi.assistant` с текстом | отдельное сообщение |
| Следующее сообщение агента (план, вопрос, карточка) | своя запись | отдельное сообщение, как в Telegram-боте |
| Вставка (`/terminal`, `/tasks`…) | `bench.insert` | там, где поставлена; × убирает |
| Открытая задача из `/tasks` | новая запись-карточка | новое сообщение под вставкой |

Правила, которые станут тестами (`cargo test`), а не комментариями:

1. Новое от агента всегда встаёт **после последней записи журнала и перед очередью**.
2. Очередь идёт в порядке `InboxDoc`. «Отправить сейчас» переносит элемент в начало очереди —
   к агенту — и Pi забирает его на ближайшей границе шага.
3. Когда Pi забирает сообщение из очереди, оно становится записью журнала с тем же текстом и
   **на том же месте экрана** — меняется только статус.
4. Шаги и время считаются на сообщение, на которое агент отвечает.
5. Вставка стоит там, где её поставили; если в композере было неотправленное сообщение — после него.

### Протокол агент → Bench (вместо формата Hermes)

- `thread.open {id}` → `{entries: [...], queue: [...], inserts: {...}, head: seq}` — снимок.
- `thread.append {seq, entry}` — новая запись журнала (из `subscribeCommits`).
- `thread.patch {seq, delta}` — дописывание текста идущего ответа (стрим токенов).
- `thread.queue {items}` — очередь целиком при каждом изменении `InboxDoc`.
- Переподключение: `thread.open {id, since: seq}` — только то, что пропустил.

Удаляются: `history()` в формате Hermes, `store.addMessage` и второе хранилище сообщений,
`message.user/start/tool.start/tool.complete` для треда, `src/history.rs`.

### Отрисовка (как в Zed)

Тред рисуется через `gpui::list` + `ListState`: рисуются только видимые элементы, высоты
меряются и кешируются, прокрутка к элементу — по индексу. Это то, на чём Zed держит длинные
буферы; 3000 элементов для него — ничто. Навигация чёрточками справа — `scroll_to(index)`
по сообщениям человека, без пересчёта пикселей. Уходят `settle`, `thread_cache`, `rows_shift`,
ручная виртуализация.

### Модули: как в Zed (аналог Angular/Nest для Rust + GPUI)

В Rust роль модуля Angular/Nest играет **крейт** в cargo-workspace: у него свой `Cargo.toml`,
свой публичный API (`pub` — вход и выход), свои тесты, и снаружи видно только то, что он отдал.
Ровно так устроен Zed: `crates/editor`, `crates/project`, `crates/workspace`, `crates/ui`… —
больше двухсот маленьких крейтов, и это самая известная модели структура GPUI-приложения.

| Ваш уровень (Angular) | В GPUI / Zed | В Bench |
|---|---|---|
| Элемент (директива) | `#[derive(IntoElement)]` + `RenderOnce`: без состояния, вход → вид | `crates/ui`: кнопка, поле, `block_head`, строка списка, текст |
| Сервис | `Entity<Model>` или `Global`: состояние и логика без вёрстки | `crates/thread` (журнал), `crates/agent_client` (протокол), `crates/tasks`, `crates/ssh` |
| Модуль / компонент | крейт с `Entity<View>` (`impl Render`), который читает свой сервис | `crates/thread_view`, `crates/composer`, `crates/sidebar`, `crates/inserts/*` |
| Блок / страница | панель или pane в `Workspace` | окно: сайдбар + тред + статус-бар (`crates/bench` — только сборка) |

Правила:

- крейт зависит только от тех, что ниже его по таблице; элементы не знают о сервисах;
- у каждого крейта в `lib.rs` первые строки — что он даёт и что берёт; всё прочее приватно;
- сервисы без GPUI тестируются обычным `cargo test -p thread` за секунды;
- маленький крейт ещё и собирается быстро: агент пересобирает только то, что тронул
  (в задаче про MCP было 22 сборки всего приложения).

### Элементы: одна коллекция, ни одного пикселя руками

Что есть сейчас:

- Библиотека одна — `gpui-kit` 0.8 поверх GPUI. В ней уже есть всё, что было во Flex: кнопка,
  поле, textarea, чекбокс, переключатель, select, слайдер, date picker, таблица, дерево, меню.
- Раскладка в GPUI — flexbox с шагами как в Tailwind: `.flex().items_center().justify_between()`,
  отступы `gap_1` = 4 px, `gap_2` = 8 px, `p_3` = 12 px. Это уже «понятия, а не пиксели».
- Нет **своего слоя**: поля создаются напрямую из `gpui-kit` в 60 местах, кнопки — в 19,
  ещё 102 места с `px(…)` руками. Поэтому поля бывали разной высоты, а `FIELD_H` в коде 28,
  хотя AGENTS.md говорит 32.

Что будет: `crates/ui` — единственный, кто трогает `gpui-kit` и пиксели. Остальной код
собирает экран только из него:

| Элемент | Что это | Что задаётся снаружи |
|---|---|---|
| `Text` (`body`, `muted`, `small`, `mono`) | вся типографика: размер, интервал, цвет | только вариант |
| `Field`, `TextArea`, `Search` | одна высота, одна рамка, один фокус | плейсхолдер, значение, событие |
| `Checkbox`, `Switch`, `Select` | обёртки `gpui-kit` в нашем виде | подпись, значение |
| `Button` (`primary`, `ghost`, `danger`, `icon`) | одна высота с полем | подпись или иконка, действие |
| `Block` (`head` + тело) | рамка, скругление, шапка 32 px | заголовок, действия справа, содержимое |
| `Row`, `Stack` | ряд и столбец с шагом `Gap::S/M/L` (4/8/12) | шаг, выравнивание: `start/center/end/between` |
| `Form` | поля в столбец, кнопки справа внизу | список полей, Save/Cancel |
| `List`, `ListRow` | строка списка: иконка, текст, действия на hover | данные строки |

Правила для агента: «нужна кнопка — `ui::Button`», «нужен ряд — `ui::Row::new(Gap::M)`»;
`px(` вне `crates/ui` не пишется — это проверяет тест (grep по исходникам в `cargo test`).
Перед разделением снимаются скриншоты текущих экранов (`shot.sh`, демо-режимы) — это эталон:
после переезда каждый экран должен совпасть с ним.

### Структура кода (под маленькую модель)

```
crates/ui/             элементы: текст (вся типографика), кнопка, поле, block_head, строки
crates/thread/         журнал треда, без GPUI: item.rs, log.rs, order.rs + тесты порядка
crates/agent_client/   протокол к агенту (thread.open, thread.append …), без GPUI
crates/thread_view/    тред на gpui::list: message.rs, work.rs, queue_item.rs
crates/composer/       поле ввода, вложения, диктовка
crates/sidebar/        проекты и треды
crates/inserts/        по крейту на вставку: terminal, tasks, tools, browser
crates/bench/          main.rs: собирает окно из крейтов выше, своего кода почти нет
agent/src/thread.ts    журнал Pi → протокол
```

Правила для всего проекта:

- файл ≤ ~400 строк, одна ответственность, имя файла говорит, что внутри;
- комментарий говорит, что код делает и почему — без истории правок (история — в git);
- `docs/map.md` — одна страница «где что», с типографикой и порядком треда;
- `bench-kit` сокращается до того, что не выводится из кода (look-правила, ship.sh);
  справочники по gpui остаются отдельно и не читаются по умолчанию;
- AGENTS.md: «новая задача — новый тред».

## 4. Порядок работ

> Общий порядок теперь в [architecture.md](architecture.md), §5: тред переписывается внутри
> него (шаги 2–3). Протокол агента (шаг 1 ниже) уже сделан.

Каждый шаг — отдельный коммит, приложение собирается и работает между шагами.

1. **Протокол в агенте** — `agent/src/thread.ts`, снимок + append + queue из журнала Pi, тесты
   на порядок в `agent/test/`. Старые события пока шлются параллельно.
2. **Ядро треда в Bench** — `crates/thread/` (первый крейт workspace), правила порядка как тесты.
3. **Новая отрисовка** — `crates/thread_view/` + `crates/ui/` на `gpui::list`, переключение на новый протокол.
4. **Удаление старого** — `history.rs`, Hermes-события, `turns`, `queue`, `after`, `settle`,
   `thread_cache`, второе хранилище сообщений.
5. **Коллекция элементов** — `crates/ui`: текст, поля, кнопки, блоки, ряды; скриншоты до и после.
6. **Разнести остальное по крейтам** — sidebar, composer, вставки, окружение проекта; `app.rs` распадается на сервисы этих крейтов.
7. **Документация под агента** — `docs/map.md`, сокращённый скилл, AGENTS.md.
8. **Проверка** — ваш агент на Qwen получает 3 типовые правки в новом треде; цель — до ~15 шагов.

Что может отлететь на время: живой стрим шагов субагентов, «изменённые файлы» под ответом,
источники — переносятся в новые элементы на шаге 3, но в первую очередь — порядок и очередь.
Данные (`~/.bench`) не трогаются: журнал Pi остаётся тем же, меняется только то, как его читают.
