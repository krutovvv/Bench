# Проекты: где работает агент и где делается работа

Как Bench работает с проектами на этом Mac и на серверах — одной реализацией с разными
настройками, а не отдельными путями «для удалённых». Почему всё устроено вообще так —
[architecture.md](architecture.md).

## 1. Три понятия

| Понятие | Что это | Где настраивается |
|---|---|---|
| **Агент** | процесс агента Bench (`agent/`): ведёт треды, держит модель, голос, Telegram, расписание. Есть всегда на этом Mac; на сервере — если его туда поставили | шестерёнка: список агентов, у каждого свои провайдеры, модель, голос |
| **Машина** | где выполняется работа: команды, файлы, `/terminal`, `/files`. Этот Mac или хост из `~/.ssh/config` | `~/.ssh/config` (единственное место, где описано подключение) |
| **Проект** | имя, окружение (душа, MCP, скиллы, промпты, расписание, бот), **его агент**, **его машина и папка** на ней | окружение проекта |

В сайдбаре проект всегда один и выглядит одинаково. Где он и кем ведётся — видно только в его
окружении (блок «Где работает»).

## 2. Сочетания

| Агент | Машина | Пример | Зачем |
|---|---|---|---|
| Mac | Mac | Bench (`~/Projects/bench`) | обычная работа в папке |
| Mac | сервер | тема WordPress на проде клиента; аудит сервера под атакой | на сервер ничего не ставится, туда не уходят ни модель, ни ключи. Как агент в Warp |
| сервер | тот же сервер | dev, rpi | живёт без Mac: Telegram круглосуточно, расписание, локальная модель и GPU |

Четвёртое сочетание (агент на одном сервере, машина — другой) получается из тех же частей и
отдельно не делается.

## 3. Агенты

- Bench держит соединение с каждым агентом: с локальным — напрямую, с серверным — через SSH-туннель
  (`connection.rs`). Это **один список агентов**, у локального ключ `local`, у серверного — его
  SSH-алиас. Любая команда треда идёт агенту его проекта.
- **Версия.** Серверный агент обновляется так же, как локальный: при подключении, если он простаивает
  (если занят — при следующем подключении). Статус и версия видны в шестерёнке.
- **Шестерёнка** — список агентов («Этот Mac», `dev`, `rpi`, «+ Агент на сервере»). У каждого —
  те же разделы, что сейчас у Mac: провайдеры и модель, голос, общий Telegram-бот. Страница агента
  читает и пишет настройки **этого** агента через его соединение: код настроек в агенте один и тот же.
  «Внешний вид» — общий для Bench, не агента.
- Своя сеть у каждого агента: на `dev` модель по `127.0.0.1`, у Mac — по адресу в локальной сети.
  Поэтому настройки не копируются между агентами, а правятся у каждого.
- Ключи, не нужные провайдерам, голосу и Telegram, не хранятся отдельно: ключ MCP-сервера пишется
  в его `mcp.json`.

## 4. Проекты

- **Проект хранит агент, который его ведёт** (таблица `projects` в его `bench.sqlite`, окружение в
  его `~/.bench/projects/<id>`). Сайдбар собирает проекты всех агентов, как уже собирает их треды.
- **Host агента** — его собственное окружение (машина, на которой он стоит: установка, сборка,
  обслуживание). У Mac это «Host», у серверного агента — проект с именем сервера («Dev», «RPi»).
  На серверном агенте может быть сколько угодно своих проектов рядом с его Host.
- **Машина и папка проекта**: `machine` (`local` с точки зрения его агента, или SSH-алиас) и
  `folder` на ней. Папки может не быть.
- Новый проект: имя → агент (по умолчанию этот Mac) → машина и папка.

## 5. Машина: как работа делается на сервере

Pi Durable даёт каждой беседе **среду выполнения** — `ExecutionEnv` (файловая система и оболочка,
`@earendil-works/pi-durable/env`). Все инструменты Pi (`read`, `write`, `edit`, `bash`) работают
только через неё. Сейчас агент даёт всем беседам `NodeExecutionEnv` — свою машину
(`runtime.ts`, `env:`).

- `env` получает `conversationId` беседы → её проект → его машина. Для `local` — как сейчас
  `NodeExecutionEnv`; для SSH-алиаса — **`SshExecutionEnv`** (`agent/src/ssh-env.ts`): та же
  `ExecutionEnv`, но через SSH. Pi не меняется, инструменты не знают, где они работают.
- **Одно постоянное соединение на сервер**: OpenSSH с `ControlMaster`/`ControlPersist` (свой
  `ControlPath` в `~/.bench/ssh/`). Каждая команда и каждая файловая операция идёт по нему без нового
  рукопожатия. Подключение целиком описывает `~/.ssh/config` (ключи, `ProxyJump`, порт) — Bench его не
  дублирует.
- Файловые операции — командами POSIX по тому же соединению (`cat`, `stat`, `find`, `mv`, `mkdir`),
  запись — через stdin. Сервер нужен только с `sh` — без Node и без установки чего-либо.
- Промпт говорит агенту, где он работает: «машина `wp-prod` (user@host), папка `/var/www/…`».
- `ssh_run` (вставка `/terminal`) и `remote_files` (`/ftp`) без явного хоста берут машину проекта.

## 6. Bench: одна дорожка к машине проекта

Всё, что Bench делает с машиной треда, идёт через агента треда, а не через свой SSH:

- `/files` — `GET /api/fs/…` агента; агент читает с машины проекта той же `ExecutionEnv`.
- **Файл из треда** (`MEDIA:/путь`, файл, присланный агентом): если машина не этот Mac — Bench
  скачивает его через `/api/fs` агента во временную папку (`~/.bench/cache/<машина>/…`) и открывает.
  Так же, как Telegram-бот присылает файлы.
- `/terminal` — терминал машины проекта (`thread_machine()`): для серверного агента — его сервер, для
  проекта «агент Mac, машина сервер» — этот сервер. Терминал — единственное, что Bench открывает по
  SSH сам (ему нужен живой pty).

## 7. Доступы в окружении — два раздела

- **Машины (SSH)** — хосты из `~/.ssh/config`. Общие для Mac; проект ссылается на одну как на свою
  машину, агент может ходить и на другие (`ssh_run` с хостом).
- **Файловые хосты (SFTP, FTP)** — свои у каждого проекта, с ними работают `/ftp` и `remote_files`.

## 8. Telegram

Бот принадлежит проекту и работает там, где работает агент проекта. Бот проекта на серверном агенте
отвечает круглосуточно; бот проекта на агенте Mac — пока Mac включён. Окружение говорит об этом прямо.

## 9. Порядок

Каждый шаг — коммит, приложение работает между шагами.

1. Один список агентов в Bench (`local` + серверные), маршрут команд по агенту проекта.
2. Агенты в шестерёнке: статус, версия, настройки каждого через его соединение; «+ Агент на сервере».
3. Проекты хранит их агент; Dev и RPi становятся Host своих агентов; на серверном агенте можно
   завести проект.
4. `SshExecutionEnv` и машина проекта в агенте; блок «Где работает» в окружении.
5. `/files`, `/terminal`, открытие файлов из треда — по машине проекта, через агента.
6. Доступы: «Машины» и «Файловые хосты».
7. Ошибки, найденные по пути: удалённые треды возвращаются.
