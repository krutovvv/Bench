# Архитектура Bench: куда он будет расти и как это заложить

План переписывания треда — [thread-rewrite.md](thread-rewrite.md). Этот документ отвечает на
вопрос шире: какая структура выдержит развитие Bench без заплаток.

## 1. Что Bench на самом деле

У Bench три ядра: **проекты** (где живёт работа: агент, машина, папка), **треды** (лента блоков:
сообщения человека и агента, работа агента, вставки `/terminal`, `/browser`, утилиты…, карточки) и
**Explorer** (проект глазами IDE: дерево, документы во вкладках, тред рядом, `docs/explorer.md`).
Окно устроено как workspace в Zed (`src/workspace/mod.rs`): левый док с панелью тредов или
Explorer, центр, правый док. Настройки проекта — документ в Explorer, шестерёнка — страница в центре.

Значит, у Bench одна идея — **лента, в которую разные модули кладут свои блоки**. Что из этого уже
так в коде, а что ещё нет, — §6.

## 2. Прогноз: где Bench будет расти

| Точка роста | Что вероятно появится | Чего это потребует от структуры |
|---|---|---|
| **Вставки** — растут чаще всего | `/git`, `/db`, `/docker`, `/logs`, `/http`, `/notes`, `/calendar`, `/image` | добавить вставку = добавить модуль, ничего не трогая вокруг |
| **Карточки** (формы и редакторы) | новые объекты окружения, больше полей, группы полей, проверки | форма описывается данными, рисуется одним рендером |
| **Секции окружения и настроек** | новые секции, другой вид (вкладки, группы, поиск) | секция — модуль; вид секций меняется в одном месте |
| **Сообщения агента** | план, вопрос, одобрение, файл, медиа, диаграмма, фоновый процесс | новый вид блока = новый рендер по `kind`; незнакомый `kind` — как текст, без падения |
| **Объём треда** | тысячи элементов, поиск, переход к сообщению, два треда рядом | ядро треда без UI, виртуальный список, ключи вместо позиций |
| **Где работает** | Mac, сервер по SSH, веб-сборка (уже есть wasm), позже Linux/Windows | логика без GPUI и без ОС; платформа — тонкий слой |
| **Агент** | новые инструменты, каналы (кроме Telegram), расписание, провайдеры | модуль агента = папка с маршрутами, инструментом, хранилищем, секцией промпта |
| **Протокол** | каждая новая вставка и блок добавляют типы | одно описание типов для Rust и TypeScript |
| **Чужие модули** (позже) | вставки и блоки сторонних авторов | те же точки расширения, что у своих |

## 3. Структура: берём готовую — Zed

Что здесь уже стало кодом и что осталось целью — §6.

GPUI — библиотека Zed, и лучшая известная структура приложения на ней — сама структура Zed.
На ней обучены и модели. Её идеи:

1. **Workspace из крейтов.** У каждой фичи свой крейт и своя функция `init(cx)`, которая
   регистрирует фичу в приложении. Приложение — список вызовов `init`.
2. **Типажи как точки расширения.** В Zed это `Item` (то, что открывается во вкладке), `Panel`
   (то, что в доке), `Settings` (типизированные настройки каждого крейта). Ядро знает только
   типаж, фичи его реализуют.
3. **Состояние у фичи.** Каждая фича держит своё `Entity<…>` и общается событиями. Общего
   объекта со всем состоянием нет.
4. **Крейт `ui`** с компонентами без состояния и **крейт `storybook`**, который показывает каждый
   компонент во всех состояниях. Это и каталог («как выглядит кнопка»), и эталон для скриншотов.

### Точки расширения Bench

| Типаж | Что это | Что реализует модуль |
|---|---|---|
| `Insert` | живая вставка в треде | ключ и слова `/`, своё состояние (serde), вид, `block_state()` для агента, восстановление |
| `Card` | форма или редактор под блоком | **схема полей данными** (`Field::text("Имя")`, `Field::secret`, `Field::select`…) и действие Save |
| `Section` | секция окружения проекта или настроек | заголовок, действия в шапке, строки, карточки |
| `BlockKind` | вид сообщения агента | `kind` из протокола и рендер; незнакомое — текстом |

Ядро треда кладёт в ленту то, что вернули модули, и больше ни о чём не знает. Новая вставка —
это новый крейт и одна строка `inserts::git::init(cx)`.

Карточки описываются данными, а рисует их один `ui::Form`. Поэтому если секции окружения
понадобится другой вид (ваш пример), он меняется в одном рендере сразу у всех секций. А новое
поле — это одна строка в схеме.

Шестерёнка тоже собирается из `Section` и `Card`: провайдеры и внешний вид — две секции.

### Слои, как ваши элементы → модули → блоки → страницы

```
ui            элементы: Text, Field, Button, Row, Block, Form, List      (никакого состояния)
core          сервисы без GPUI: thread (журнал), protocol, devtools
features      модули: thread_view, composer, sidebar, inserts/*, sections/*, blocks/*
pages         тред, окружение проекта, шестерёнка — сборка из features
bench         main.rs: окно, init всех крейтов, платформа
```

Крейт зависит только от тех, что ниже его. `ui` ничего не знает о Bench, `core` — о GPUI.
Правило проверяется в `cargo test` по `Cargo.toml` крейтов.

### Протокол — один источник

`crates/protocol`: типы на serde. Из них через `ts-rs` генерируется
`agent/src/protocol.gen.ts`. Агент и Bench не могут разойтись: поменяли тип — не собралось
с обеих сторон.

### Агент — те же модули

Nest напрямую не подходит: агент — это WebSocket JSON-RPC вокруг Pi, а жизненным циклом
владеет Pi. Его идею берём как соглашение:

```
agent/src/modules/<name>/
  index.ts     export default { rpc, routes, tools, prompt }   ← модуль объявляет, что даёт
  store.ts     своё хранилище, если нужно
  test.ts
agent/src/server.ts   только собирает модули из списка
```

Сейчас модуль агента — файл в `agent/src/modules/` (RPC и REST одной области), инструмент — в
`agent/src/builtin/`. Вставка с агентским инструментом — это пара: папка в `src/inserts/` и
инструмент агента.

## 4. Что это даёт маленькой модели

- Задача «новая вставка» — скопировать `src/inserts/tools`, переименовать, реализовать `InsertKind`.
- Вопрос «как выглядит кнопка» решает `storybook`, а не поиск в `~/.cargo/registry`.
- Вопрос «где это» решает `docs/map.md`; «почему так» — `SPEC.md` модуля.

## 5. Порядок

Ядро переписано снизу вверх (`ui`, `protocol`, `thread`, вид треда), приложение работало между
шагами. Дальше так же: что осталось — §6, по одной вещи.

## 6. Где мы сейчас

Сделано:

- `crates/ui` + `storybook` с эталонными картинками; `bench_ui` — единственное место с размерами и
  отступами: экраны пишут `Gap` и именованные константы.
- `crates/protocol` (TypeScript для агента генерируется) и `crates/thread` (ряды из журнала Pi,
  правила порядка — тесты); тред — своя сущность `ThreadView` на `gpui::list` (`src/thread/`).
- `BenchApp` держит по одному полю на область; `Render` без побочных эффектов
  (`src/app/subscriptions.rs`); одно нажатие — один обработчик (`own_press`, без общего флага).
- Старые режимы (Tasks, Tools, SSH) и мост к Apple Reminders удалены.
- Вставки — по папке на вид (`src/inserts/<вид>/`), утилиты — `crates/devtools`.
- Окружение проекта — `src/env/`, типаж `Section` и два его вида: `SettingsForm` (реестр `FORMS`, страница настроек) и `ExplorerParts` (реестр `PARTS`, части в дереве Explorer).
- Демо — поддельный агент, как `FakeFs` в Zed (`src/client/fake.rs`, `src/demo/`): продуктовый код о нём не знает.
- `app.rs` разрезан по областям (`src/app/`); агент — модули (`agent/src/modules/`), ядро тредов
  `agent/src/runtime/`, хуки хода `agent/src/turn/`, оценщик `agent/src/judge/`.

Осталось:

- `InsertKind` и `Section` пока получают `&mut BenchApp`: вставки и секции ещё не свои
  `Entity` с событиями, поэтому не вынесены в крейты. Это следующий шаг: по одной вставке,
  начиная с `/tools`.
- Карточки описываются кодом секции, а не данными (`Field::text…`) — схема полей ещё не сделана.
- `BlockKind` (виды сообщений агента по `kind`) не выделен: каждый вид ряда — свой файл в
  `src/thread/rows/`.
- Индекс тредов и поиск агента лежат в `bench.sqlite`, а не в документах Pi.
