# Структура Bench: куда класть новое

Где что лежит, говорит скилл `bench-map`. Этот скилл говорит, как решить, куда класть новое и когда
переделать старое. Если правила спорят, побеждает то, что выше: сначала структура под развитие,
потом дерево файлов, понятное без документации, потом язык Rust и Zed.

---

## 1. Структура под прогноз развития (главное)

### Что такое Bench

У Bench три ядра, равных по важности. Каждое — своя часть кода со своей точкой расширения.

| Ядро | Что это для человека | Где в коде | Как расширяется |
|---|---|---|---|
| **Проекты и агенты** | где живёт работа: агент этого Mac или сервера, машина, папка | `src/app/places.rs`, `src/app/agents.rs`, `src/client/`, `src/env/` | новая часть окружения — `Section` в `src/env/`: `SettingsForm` (поля настроек, `FORMS`) или `ExplorerParts` (части в Explorer, `PARTS`) |
| **Треды** | разговор с агентом, его работа, вставки `/terminal`, `/browser` и утилиты, каждая своим словом (`/base64`, `/json-yaml`…) | `crates/thread`, `src/thread/` (тред на экране — сущность `ThreadView`), `src/inserts/` | новая вставка — `InsertKind` в `src/inserts/<вид>/`; её методам говорят, в каком треде она (`ThreadRef`) |
| **Explorer** | проект глазами IDE: дерево, документы во вкладках, тред рядом | `src/explorer/`, `src/workspace/` | новый вид документа — вариант `DocKey` и его `Item` (`src/explorer/pane/item.rs`, как `Item` в Zed); новая панель дока — вариант `Panel` в списке своего `Dock` (`workspace/dock.rs`) |

Окно устроено как workspace в Zed: левый док (панель тредов или Explorer), центр (тред,
документ, страница настроек), правый док (тред рядом с кодом). Общие элементы — `crates/ui`.

### Прогноз: куда Bench, скорее всего, пойдёт

Его составляет человек — он лучше знает, куда нужно. Этот список не задача на сейчас. Это
мерка: новое решение не должно мешать ни одному из этих направлений.

- **Explorer растёт в полноценную, но узкую IDE.** LSP через агента (ошибки, hover, переход
  к определению). Терминал в нижнем доке на машине проекта. Git в полях редактора и диффы. В
  тред отправляются выделение, ошибки линтера, вывод терминала. Новые виды документов:
  картинка, просмотр Markdown, дифф.
- **Доки держат больше панелей.** Второй тред рядом (есть: второй `ThreadView` в правом доке).
  Список проблем. Нижний док.
- **Проекты на серверах** работают так же, как локальные, включая Explorer.
- **Вставок становится больше.** Одни часть треда, другие похожи на маленькие приложения в
  закреплённом треде (утилиты).
- **Агент растёт модулями:** инструменты, каналы кроме Telegram, расписание, провайдеры.
- **С кодом работает слабая локальная модель.** Всё должно быть очевидным и небольшим.

### Как решать, куда класть новое

Перед изменением напиши в сообщении ответы на три вопроса, по порядку.

1. **Что это по виду?** Выбери одно:
   - панель дока (что-то слева или справа целиком);
   - документ в центре (вкладка);
   - вставка в тред;
   - часть окружения проекта (`Section`);
   - общий элемент (`crates/ui`);
   - сервис связи с агентом (`src/client/`);
   - инструмент или модуль агента (`agent/src/builtin/`, `agent/src/modules/`).
2. **Какой сосед того же вида уже есть?** Открой его файл и назови его. Новое строится так же.
3. **Встанет ли новое без исключений?** Представь следующую такую же вещь. Если для неё придётся
   писать `if kind == "…"`, особый флаг или «а тут по-другому», поправь общее, а не подпирай его.
   Проект молодой, им пользуется один человек: переписать слой дешевле, чем жить с костылём.
   Если правка общего намного больше, скажи об этом человеку и спроси.

### Признаки заплатки — и что было вместо неё

Это настоящие случаи из истории Bench. Узнавай их заранее.

| Заплатка | Что сломалось | Как сделали правильно |
|---|---|---|
| Одно поле `project_env` на всё приложение | настройки одного проекта подменялись Explorer'ом другого; Remove удалял сервер не в том проекте | `envs: HashMap<проект, ProjectEnv>`; каждый вид читает окружение своего проекта |
| Ключ вкладки без проекта (`DocKey::Part { kind, name }`) | вкладка показывала часть другого проекта с тем же именем | ключ несёт проект: `DocKey::Part { project, … }` |
| Второй редактор со своим сохранением для того же файла (`lsp.json`) | два пути сохранения одного и того же | одна сущность — один путь: у каждого сервера своя запись и свой статус, как у MCP |
| Вкладки в заголовке окна | перетаскивание вкладки таскало окно | у центра своя полоса вкладок под заголовком, как у pane в Zed |
| Иконки действий на каждой строке дерева | шум, нестандартно для IDE | контекстное меню, как в любой IDE |
| Три копии `icon_button` в разных файлах | расходились по виду | один `bench_ui::icon_button` и один `head_icon_button` |
| Строка `"general"` в десятке мест | ломалось для Host сервера (`dev:general`) | `ProjectKey::HOST`, `is_host()`, `project_or_host()` |
| «Файл рядом» в правом доке | вторая механика открытия файла рядом с первой | правый док держит панель (сейчас — тред); файлы открываются вкладками |
| Открытый тред — поля `BenchApp` (`active_thread`, `composer`), рисуется методами `BenchApp` | второй тред рядом пришлось бы рисовать подменой: обработчики после подмены действовали бы не на тот тред | тред — своя сущность `ThreadView` со своим состоянием и композером; всё, что вид просит у приложения, получает `ThreadRef` и никогда не читает вид |
| Состояние установки по наличию папки `node_modules` | прерванная установка не повторялась, агент не стартовал | метка `.lock-installed` пишется только после успешного `npm ci` |
| Протокол «профилей», `Cmd`/`Evt` и строковые методы | клиент и агент расходились молча; каждая новая функция добавляла вариант в огромный enum | один тип на метод в `crates/protocol` (`Request` с типом ответа), одно `Event`; агент типизирован тем же списком |
| Опросы: статус агента раз в 10 с, задачи раз в 4 с, вход в MCP раз в 3 с | лишняя нагрузка, задержки, гонки | агент сам говорит, что изменилось (`Event::EnvChanged`, `ThreadsChanged`) |
| Копии в своей базе того, что хранит Pi (сообщения для поиска, модель треда) | копии устаревали (`speed`, `model`) | индекс поиска строится из коммитов Pi; модель одна — общего агента |
| Пять отдельных полей «взведено для удаления» | разные виды, разное поведение Esc | одно `app.armed` (`app/armed.rs`) и `bench_ui::confirm_buttons` |
| ≈95 полей разных областей в `BenchApp` | любая новая функция росла в один объект | состояние области — структура в её папке (`sidebar/state.rs`, `media/state.rs`, `thread/store.rs`…), в `BenchApp` одно поле на область |
| Счётчики треда (токены, скорость) в общем статус-баре | мигали при переключении тредов, было непонятно, чьи они | они — часть треда (`thread/meters.rs`), стоят в его заголовке рядом с репозиторием |
| «/»-слова вставок списком и `match` отдельно от видов вставок | новый вид правился в трёх местах | вид сам говорит своё слово и варианты (`InsertKind::word`, `choices`) |
| `if self.demo` в продуктовом коде и `BENCH_DEMO_*`, читаемые при отрисовке | продуктовый код знал про демо, каждый кадр спрашивал окружение | демо — поддельный агент, как `FakeFs` в Zed: шов `src/client/fake.rs`, ответы `src/demo/agent.rs`, хуки читаются один раз (`src/demo/hooks.rs`), состояние — в своей временной папке (`connection::use_state_dir`) |
| Общий на приложение флаг «щелчок занят» | ~47 мест должны были помнить про него | что обрабатывает щелчок, останавливает его распространение (`bench_ui::own_press`); тред берёт только необработанное нажатие (`ThreadView::press`) |
| Отрицательные отступы, чтобы отменить паддинг блока | тело вставки боролось с рамкой | вид вставки сам говорит, как тело сидит в блоке (`InsertKind::inset`) |
| Побочные эффекты в `Render` (загрузка промптов, поток браузера, история) | работа зависела от кадров | наблюдатели: `observe_changes`, `follow_shown` (`src/app/subscriptions.rs`), как подписка на активный item в Zed |
| Таймер спрашивает, доиграл ли клип | лишний опрос каждые 500 мс | плеер сам говорит о конце (`Playback::ended`) |
| Карточка сервера, «Show all», рамка кода, чип написаны по нескольку раз | расходились по виду | один элемент в `bench_ui`: `settings_card`, `fold_more`, `code_frame`, `chip` |
| Два имени одного понятия (`profile` и `agent`, `session` и `thread`) | читающий не понимал, одно это или два | одно слово — одно понятие; старые имена в базе переименовываются миграцией (`renameOld`) |

Общий рисунок: **состояние хранится в одном месте и знает, чьё оно**; **одна вещь — один
путь**; **новое встаёт в существующий тип, а не рядом с ним**.

### Прежде чем закончить

Снова представь следующую вещь того же рода (вопрос 3). Если она потребует исключения, ты ещё не
закончил.

## 2. Дерево файлов, понятное без документации

### Главное правило

Просьба вроде «поправь статус-бар внизу» должна приводить в нужную папку **по одному её
имени**, без скиллов и без карты `bench-map`. И человек, и агент открывают дерево и сразу видят, где
что.

Аналогия, из которой это правило выросло, — конструктор сайтов, где блоки разложены по
папкам «шапки», «середина», «подвалы». Компилятору всё равно, лежат все блоки в одной папке
или в трёх. Человеку и агенту — нет: с папками «поправь шапку» не уведёт в подвал.

### Как устроен `src/`

- **По месту в окне** — то, что живёт в одной части окна: `titlebar/`, `sidebar/`,
  `thread/`, `settings/`, `workspace/` (раскладка и доки). В чате статус-бара нет: проект, репозиторий и
  счётчики треда под его композером, агент в подвале левого дока; у Code свой статус-бар
  (`explorer/statusbar.rs`).
- **По фиче** — то, что занимает несколько частей окна: `explorer/` (внутри папки по месту и
  работе, как у Zed: `tree/` — его часть в сайдбаре, `pane/` — документы в центре, `search/`,
  `code/`), `inserts/` (папка на вставку), `env/` (окружение проекта).
- **Внутри области — по тому, что видно**: `thread/rows/` (по файлу на вид строки ленты),
  `thread/composer/` (следующее сообщение). Когда в папке набирается десяток файлов разной
  природы, разложи их так, как это разложено в окне.
- **Состояние области — в её папке** (`<область>/state.rs` или `store.rs`): `BenchApp` держит по
  одному полю на область (`app.sidebar`, `app.media`, `app.threads`, `app.inserts`, `app.gear`…).
  Новое поле — в структуру своей области, не в `BenchApp`.
- **Сервисы** — то, что не рисует: `client/` (связь с агентом: `rpc/`, `rest/`,
  `connection.rs`, `launch.rs`, `service.rs`, как крейт `client` в Zed), `media/`, `system/` (машина:
  ssh-конфиг, уведомления).
- **`app/`** — только то, что принадлежит всему приложению: модель данных, события агента,
  клавиши, меню, где живут проекты.
- **`demo/`** — поддельный агент для снимков: фикстуры по темам (`env.rs`, `threads.rs`, `journal.rs`),
  хуки (`hooks.rs`), что они просят от окна (`script.rs`). Продуктовый код о нём не знает.
- **Агент (`agent/src/`) так же**: `runtime/` (ядро тредов и его части — по файлу на работу,
  `rt.<часть>`), `machine/` (где работают инструменты), `mcp/`, `lsp/`, `builtin/`
  (инструменты), `turn/` (что хуки хранят о ходе), `judge/` (оценщик), `modules/` (маршруты); в
  корне — сервер, конфиг, хранилище, промпт.
- **Связь клиента и агента — `crates/protocol`**: новый метод = тип запроса с типом ответа в
  `rpc.rs`; то, что агент сообщает сам, — вариант `Event`. Никаких строковых методов и опросов.
- **В корне `src/` — только `main.rs` и `app.rs`.** Всё остальное в папке, названной по смыслу.

Новая папка появляется, когда у вещи появляется своё место в окне или своя фича. Не раньше:
одна функция — не повод для папки.

### Небольшие файлы

- Файл больше **~500 строк** режь по тому, что делают его части. Имя каждого куска — его
  работа: `changed_files.rs`, `file_finder.rs`, `project_search.rs`, а не `utils.rs`,
  `helpers.rs`, `misc.rs`.
- Каждый файл начинается с `//!`-комментария в две–пять строк: что здесь и где соседи.
- Агент должен открыть файл целиком и не захлебнуться контекстом.

### Переиспользование

- **Элемент, который нужен в двух местах, живёт в `crates/ui`** (`bench_ui`), один на всех.
  Размеры и отступы — только там (`crates/ui/src/metrics.rs`, по группам: окно, линии,
  всплывающие окна, сайдбар, тред, композер…): именованные константы и шаги `Gap` (`.gap(Gap::M)`,
  `.px(Gap::L)`), `bench_ui::row`/`stack`; в экранах ни числа пикселей, ни голых `gap_2`, `px_3`. Пороги поведения (допуск щелчка) — именованные `const` рядом с кодом.
- **Механизм, который нужен двум фичам, — один**, с параметром, а не два похожих.
- **У семейства похожих вещей — один каркас.** У виджета есть рамка, шапка и тело: контейнер один,
  каждый приносит своё содержимое; поменял контейнер — поменялись все.
- **Соседи устроены одинаково** (вставки, секции окружения, вкладки шестерёнки). Прикидывай, что того
  же рода появится ещё, и закладывай общее (реестр, контейнер, трейт) с первых строк.
- Прежде чем писать новое, найди похожее (`grep`) и возьми его. Если оно почти подходит —
  доведи его, а не копируй.
- Но **не переусердствуй**: общая абстракция появляется на втором реальном случае, а не на
  воображаемом. Опора — прогноз из первой части, а не «на всякий случай».

## 3. Язык: термины Rust и Zed

Общепринятые слова понятны всем, свои нет. Поэтому:

- **Называй по-зедовски:** workspace, dock, panel, pane (центр), item (документ во вкладке),
  компонент `ui`. Точки расширения — трейты, как `Item` и `Panel` в Zed (у нас `InsertKind`,
  `Section`).
- **Rust-модули, а не «модули» из других фреймворков:** папка с `mod.rs` — модуль; крупная
  независимая часть — крейт в `crates/`.
- **Никаких личных терминов в коде.** Слова «страница / секции / блоки / элементы» из
  конструктора сайтов — это способ думать о структуре, а не имена для кода. Как эта мысль
  ложится на Rust и Zed:

| Как думает человек (конструктор сайтов на Angular) | Как это называется в Bench (Rust, Zed) |
|---|---|
| страница — само приложение | `Workspace`: окно, `BenchApp` + `src/workspace/` |
| секции (слева, по центру, справа) | доки и центр: левый док, `Center`, правый док |
| блоки в секции | панели доков (`Panel` в `Dock`), документы в центре (`DocKey`), вставки (`InsertKind`) |
| элементы, общие для нескольких блоков | компоненты `crates/ui` (`bench_ui`) |
| модуль со своими сервисами, компонентами, директивами | папка-модуль фичи (`src/explorer/`, `src/inserts/terminal/`) |
| сервисы (сеть, данные) | `src/client/`, `src/system/` |
| общий пайп для нескольких модулей | функция или тип в общем модуле (`crates/ui`, `src/app/`) |

## Где ещё смотреть

- скилл `app-playbook` — что общего у Bench и его приложений-соседей; `scripts/tree-check.sh` — правила этого скилла как проверка.
- `AGENTS.md` — как здесь работать; скилл `bench-concepts` — понятия Bench.
- скилл `bench-map` — где лежит то, что нужно поменять.
- `references/architecture.md` этого скилла — почему так; `src/explorer/SPEC.md` — окно и Explorer, фазы IDE.
- `.agents/skills/bench-kit/SKILL.md` — как менять UI и проверять изменение снимками.

Когда меняешь структуру — обнови скилл `bench-map` (дерево), `SPEC.md` модуля и этот скилл, если
поменялось правило. Устаревшая документация вредит слабой модели больше, чем отсутствующая.
